# 性能测试报告

## 1. 测试环境

| 项 | 值 |
|---|---|
| CPU | 13th Gen Intel Core i5-13500H，16 逻辑核 |
| 内存 | 5.8 GiB |
| 系统 | WSL2，Linux 6.6.114.1-microsoft-standard |
| 编译器 | g++ 15.2.0 |
| 构建 | C++17，`-Wall -Wextra -pedantic` |
| 服务端配置 | 6 worker，MySQL 连接池 6 条 |
| 负载工具 | 仓库自带 `chat_loadgen` |

服务端、负载驱动器和 MySQL 运行在同一台机器上，因此下列数字包含客户端竞争、宿主调度和 WSL2 虚拟化开销，不代表独立服务器或生产环境容量。

## 2. 负载模型与口径

两种模式都使用登录负载：每条连接建立后重复发送

```text
login:<username> <password>\n
```

并等待完整欢迎语。每条并发连接独占一个 worker 线程和一个账号，所以并发数不能超过账号数。

| 参数 | 模式一 | 模式二 |
|---|---|---|
| 每连接请求数 `R` | 2000 | 50 |
| 单请求超时 | 1000 ms | 5000 ms |
| 目的 | 低并发、高请求数，观察吞吐平台 | 高并发、短轮次，观察排队延迟与稳定性 |

指标定义：

- **吞吐**：成功请求数 / 计时窗口。计时从启动 worker 线程前开始，包含建连和线程启动，因此略低于纯请求处理吞吐。
- **错误率**：`failures / attempts`。一条连接收到错误响应后，该连接剩余计划请求计入失败，所以失败请求数不等于失败连接数。
- **P50 / P95 / P99**：只统计成功请求的端到端延迟，失败和超时请求不进入分位数样本。
- 表中吞吐为各轮成功吞吐的算术平均；分位数按轮次记录，不把不同轮次的样本合并重算。

## 3. 模式一：低并发、高请求数

每条连接 2000 次登录，单请求超时 1000 ms。

| 并发 | 轮数 | 请求数 | 吞吐均值 (req/s) | P50 (ms) | P95 (ms) | P99 (ms) | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 4 | 3 | 24,000 | 12,968 | 0.301 | 0.398 | 0.453 | 0 |
| 8 | 3 | 48,000 | 19,183 | 0.413 | 0.534 | 0.595 | 0 |
| 11 | 3 | 66,000 | 22,562 | 0.483 | 0.608 | 0.669 | 0 |
| 16 | 3 | 96,000 | 22,822 | 0.696 | 0.839 | 0.908 | 0 |
| 32 | 3 | 192,000 | 22,855 | 1.389 | 1.564 | 1.666 | 0 |

追加探针：并发 10 为 21,607 req/s，并发 12 为 22,722，并发 13 为 22,711，并发 14 为 22,930；并发 16 的中途复验为 22,565。

**观察**：并发从 4 增加到 11 时吞吐持续上升；约 11 个并发后进入约 2.2 万 req/s 的平台，继续增加并发主要增加排队时间，P99 从 0.669 ms 上升到 1.666 ms。这里的“拐点”是按本批数据“进入平台 ±5%”得到的实验判定，不是系统的普遍并发上限。

## 4. 模式二：高并发、低请求数

每条连接 50 次登录，单请求超时 5000 ms。

| 并发 | 轮数 | 请求数 | 吞吐均值 (req/s) | P50 (ms) | P95 (ms) | P99 (ms) | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 400 | 3+2 | 100,000 | 21,965 | 16.95 | 19.95 | 20.87 | 0 |
| 800 | 3+2 | 200,000 | 21,403 | 35.58 | 39.68 | 41.50 | 0 |
| 1600 | 3 | 240,000 | 20,878 | 73.67 | 81.59 | 88.88 | 0 |
| 3200 | 3+2 | 800,000 | 20,868 | 149.05 | 164.85 | 176.65 | 0 |

本批 400–3200 并发累计约 134 万次请求，观测到 0 失败、0 超时、0 建连失败。400、800、3200 档的轮间波动较大，表中使用全部轮次的平均，不挑最好轮次。

**观察**：吞吐维持在约 2.1 万 req/s，增加的并发主要转化为排队延迟；3200 并发时 P99 约 177 ms。该结果只说明本机、本协议、本批次下的稳定性，不是生产容量承诺。

## 5. 过载边界

线程池任务队列上限为 4096；`submit()` 失败后服务端拒绝该任务并向客户端返回繁忙提示。

| 并发 | 观测 |
|---:|---|
| 4000 | 本批未出现拒绝 |
| 4100 | 本批未出现拒绝 |
| 4120 | 新会话两轮出现 890/892 个失败请求 |
| 4135 | 某一批次首次出现 0.79% 失败，另两轮为 0 |
| 4150–4400 | 拒绝随并发增加 |

结论：**约 4.1k 并发附近进入有界拒绝区间，但边界受连接状态、预热、宿主调度和轮长影响，不是固定阈值。** 服务端日志中的拒绝条数、驱动器失败请求数和失败连接数必须分开统计，不能相互换算。

## 6. 解释与限制

当前证据支持的解释：

- 低并发模式下，约 11 个并发后吞吐进入平台，继续加压主要增加等待和尾延迟。
- 高并发模式下，超过服务端处理流水线后，等待任务逐渐填满 4096 有界队列，进入拒绝区间。
- 采样结果指向事件循环、worker 与数据库连接之间的唤醒和交接开销；没有足够证据把某一处符号占比直接当作唯一根因。

限制：

- P99 只覆盖成功请求；失败请求用错误率和失败分类单独统计。
- 短轮与长跑不能混用。本报告的模式一是短轮；同机另一次 `R=300` 的长跑观测约 16.1k req/s，明显低于短轮平台。
- 压测只覆盖登录路径；私聊包含同步落库，广播包含在线用户遍历，不能把登录吞吐外推到这两条路径。
- WSL2 不支持本批所需的 PMU cycles/instructions 采样，长跑下降不能简单归因于功耗或降频。
- 服务端、客户端和数据库共享同一台 16 逻辑核机器；系统范围 CPU 与调度统计包含驱动器、MySQL 和其他任务。

## 7. 复现

初始化数据库并启动服务端：

```bash
sudo mysql < scripts/init_db.sql
./build/src/chat_server
```

模式一并发 11（需要 11 个账号）：

```bash
./build/src/chat_loadgen 127.0.0.1 8080 11 2000 1000 \
  alice:pass123 bob:pass456 \
  u1:pass123 u2:pass123 u3:pass123 u4:pass123 u5:pass123 u6:pass123 \
  u7:pass123 u8:pass123 u9:pass123 u10:pass123 u11:pass123
```

更大并发需要扩充账号池。例如生成 3200 个压测账号：

```sql
USE chat_db;
SET SESSION cte_max_recursion_depth = 4000;
INSERT INTO users (username, password)
WITH RECURSIVE seq(n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1 FROM seq WHERE n < 3200
)
SELECT CONCAT('bench', n), 'pass123' FROM seq;
```

然后把 `bench1:pass123 ... bench3200:pass123` 传给驱动器。账号数必须不少于并发数。
